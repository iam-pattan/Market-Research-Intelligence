Banyan M&A intelligence · data access design

Who sees what, and where the wall actually stands.

The question: "We want a layered data architecture where each end user only consumes the data they are entitled to. How does that work for Claude users — does it require an extra layer for them?"

Yes — two things, both outside Claude

Identity (the user signs in through the company IdP, and their role and scope travel as claims) and an enforcement point between the data and the model — a service that authenticates the caller, resolves the role, and runs policy.guard(role, payload) before anything is returned. Claude is a client of that service, never the custodian of the raw dataset.

No — nothing inside Claude

No per-role Claude instances, no "system prompt says don't reveal financials", no output scrubbing after the fact. Once a field is in the model's context it has already been disclosed to that user. Prompt instructions are guidance, not access control; the filter must run before the data reaches the context window.

Already built in this repo

banyan_screen/policy.py is the policy decision point: 5 classification tiers, 14 roles, deny-by-default, 11 tests. build_dossiers.py fails closed on role. What is missing for production is the substrate around it — an identity source, the MCP/API enforcement point, storage-level tagging, and audit. Sections below are that map.

The six layers

Each layer has one job and one owner. A request travels top-to-bottom; data travels bottom-to-top and is narrowed at layer 4. The highlighted layer is the one that answers the "Claude users" question.

1identity

Identity & attributes

Who is asking. Corporate IdP (Okta / Entra ID / Google Workspace) authenticates; group membership maps to one role family per human; ABAC attributes (assigned verticals, regions, deal-team memberships, MNPI clearance, MFA strength) are pushed to the policy information point.

In the repo today

Not present — role is a string argument. The conceptual model (iam_hierarchy) defines the attribute set.

Production

OIDC/SAML SSO → JWT with role, scope, mnpi_clearance claims. Group-based provisioning; requester ≠ approver; same-day leaver.

2classify

Data classification at rest

What each field is. Every column carries a sensitivity tier (Public → Internal → Confidential-Financial → Restricted-PII → Restricted-MNPI) and a regulatory category (SOX / GDPR / securities). Deal-intent signals are tagged MNPI at write-time. Unknown fields default to Confidential.

In the repo today

policy.classify(key) — pattern-based, fail-closed default. Tested.

Production

BigQuery policy tags / Snowflake tag-based masking / column-level labels; lineage inherits MAX input tier; data steward proposes, second approver certifies.

3decide

Policy decision point (PDP)

Given (subject, resource, environment) → allow / mask / deny per field, plus row predicates. RBAC sets the ceiling (which tiers a job function may ever see); ABAC narrows to permitted rows (own vertical, enumerated deals, residency).

In the repo today

policy.ROLES + enforce() — the role → tier matrix, masking rules, aggregate-only flag for Data Science.

Row-level ABAC predicates: conceptual only.

Production

OPA (Rego) or Cedar policies evaluated on effective permissions; RLS predicates in the warehouse; a separate statistical-disclosure-control service for aggregates (k≥5).

4enforce

Policy enforcement point — the "Claude layer"

The only door to the data. An MCP server or API gateway that (a) validates the user's token, (b) asks the PDP, (c) executes the query with the user's row scope, (d) runs guard(role, result) to drop or mask fields, and (e) writes an audit record. Claude — in claude.ai, Claude Code, or an agent — calls this door with the user's identity and receives only what that user may see.

In the repo today

policy.guard() and the coarse pitch_visible() gate; build_dossiers.py refuses to build for non-Sales roles.

No network service yet — the guard is a library call.

Production

Remote MCP server (OAuth 2.1, per-user tokens), tools like search_targets, get_dossier, segment_stats; every tool result passes through guard before it is returned to the model.

5consume

Consumers

Where people meet the data. claude.ai chat with the MCP connector; Claude Code with the same server; published Artifact pages and BI dashboards; direct warehouse access for Finance. Each consumer inherits the user's identity — none holds its own superuser credential.

In the repo today

Static HTML reports (Leadership / tech-lead audience); per-role dossier builds.

Production

Claude Team/Enterprise with SSO; MCP connector registered org-wide; artifacts published per audience or backed by a viewer-aware data source.

6audit

Audit & governance

Proof it worked. Immutable, tamper-evident log of every decision (who, what field, which tier, purpose artifact), written to WORM storage the platform admin cannot alter. Quarterly recertification on effective permissions; break-glass that cannot reach MNPI.

In the repo today

Not present.

Production

Cloud audit logs → SIEM; one stream serving SOX ITGC, GDPR Art. 30 and insider-trading surveillance; alerts on downgrades, unmasks, exports, RLS bypass.

Classification tiers

Five ascending tiers, as implemented in policy.py. A role is granted a set of tiers, and within that set some tiers are shown only masked. The classifier maps field names to tiers by pattern; anything it does not recognise lands at Confidential-Financial so a new column is never leaked by omission. Where the conceptual IAM model goes further than the code, the description says so.

Role × tier matrix

Read straight from policy.ROLES. Governance and platform roles are deliberately not business-data consumers: they administer the controls, they do not read the records. Data Science is aggregate-only — a per-record request from a DS role is refused outright, not filtered.

How this works for Claude users

Three ways a person in the company reaches this data through Claude, and what each one needs. In every case the enforcement point (layer 4) is the same service; what changes is how the user's identity gets to it.

claude.ai chat (Team / Enterprise)

user signs in via SSO → asks Claude → Claude calls MCP tool with the user's OAuth token → PEP resolves role → guard() → filtered result → Claude answers

The MCP connector is registered once by an admin; each user authorises it with their own login. A finance analyst asking "what's HawkSoft's revenue estimate?" gets the figure; a data scientist asking the same question gets a refusal from the tool, and Claude relays it. Claude never had the number.

Needs: SSO + the MCP server. Nothing else.

Claude Code (engineers, analysts)

developer authorises the remote MCP server in the browser (OAuth) → Claude Code tools call PEP → guard() per call → local files never contain raw data

Same server, same rules. The one trap is the repository itself: if data/ with raw records is checked out locally, the file system bypasses the wall. In production the raw JSON should not be in the repo — the pipeline writes to the governed store and Claude Code reads through the MCP server.

Needs: MCP server + moving raw data out of the working tree.

Published Artifacts & dashboards

static page: whoever has the link sees everything embedded in it → share per audience, or → page fetches data at view time from a viewer-aware source

The companion Banyan Target Intelligence page embeds the full dataset — it is a Leadership / tech-lead artifact and must be shared as one. For role-specific views, either build one page per role (what build_dossiers.py already does, failing closed) or have the page load data live through the same PEP using the viewer's identity.

Needs: audience-scoped sharing, or per-role builds.

What end users need

  • A company identity (SSO) — the same login they use for email.
  • To be placed in exactly one role family by provisioning; scope (verticals, regions, deals) as attributes.
  • The MCP connector authorised once in their Claude client.
  • Nothing to learn: they ask questions; refusals come back as plain "not available for your role" messages.

What they do not need

  • A separate Claude account, model, or workspace per role.
  • Custom system prompts or "instructions" pretending to be access control.
  • A copy of the data. The dataset lives in one governed store; consumers get filtered views.
  • Trust in the model to self-censor — the model is treated as an untrusted client of the data service.

What is not a control

Failure modes that look like security and are not. Each has a concrete answer in the design.

"Tell Claude not to reveal financials."Prompt-level rule
The field is already in context; a rephrased question, a summary, or a tool that echoes it will leak. Answer: filter at layer 4 before the context window. The model only ever sees what the role may see.
Post-filtering Claude's outputOutput scrubbing / DLP on the response
Catches strings, not meaning ("roughly eighteen and a half million"). Useful as defence-in-depth for exports, never as the primary gate. Answer: input-side enforcement; output DLP only on export step-ups.
A shared service account for the MCP serverOne credential for all users
Every caller becomes the same identity and the PDP has nothing to decide on. Answer: per-user OAuth tokens; the PEP never queries with more privilege than the caller holds.
Raw data in the git checkoutdata/records, data/research in the working tree
Any Claude Code session (or any grep) reads it, wall or no wall. Answer: pipeline outputs go to the governed store; the repo keeps code, tests, templates and synthetic fixtures.
Deal intent hidden in a scoreThe MNPI side-channel found in red-team
A Banyan-fit score that moves when a deal starts is non-public deal information. Answer: tag deal-intent-bearing fields MNPI at write-time; exclude them from the Data Science mart entirely.
Aggregate differencingA user who is both DS and Sales
Subtract five own-territory raw scores from a k=6 aggregate to isolate the sixth company. Answer: mutually exclusive role families; SDC service enforces k≥5 with dominance and complementary suppression.

Governance

From the IAM model's red-teamed design. These are the operating rules that keep the layers honest over time.

Provisioning

Group-based via the IdP. One consumer family per human, enforced at grant. Every grant is request → approve → log, requester ≠ approver. Deal-team additions need Compliance co-approval — IT alone can never grant MNPI access. Unresolved attributes → alarmed pending state, deny.

Access reviews

Quarterly recertification on effective permissions across a person's full role + attribute set; MNPI, PII and financials first. Toxic role-pair detection on every identity. Exceptions are named, time-boxed, auto-expiring and visible in a "who can see company X" simulator.

Audit

Immutable, tamper-evident, on WORM storage the platform admin cannot alter. Every classification change, wall-crossing, bulk export, PII unmask, cross-territory read and RLS-bypass attempt is logged with its purpose artifact; sensitive events alert in real time.

Break-glass

Independently approved, alarmed, time-boxed, domain-bounded. Excludes Restricted-MNPI and cannot override a blackout window or an ethical wall. Frequency is tracked as a boundary-health signal.

Red-team findings that shaped the model (3 Critical, all fixed)

CRITICAL
Fit-scores were an unwalled MNPI side-channel — Finance and Sales could infer deal intent from score movement.
Fixed: write-time mnpi_tag; deal-intent signal excluded from the DS mart.
CRITICAL
The data steward was a single-party root of trust and could silently downgrade a tier.
Fixed: maker-checker on every downgrade / de-identification / retag; real-time downgrade alerts.
CRITICAL
No person-level role exclusion — stacking finance + leadership gave near-total reach.
Fixed: mutually exclusive role families; authorisation and recertification evaluate effective permissions.

Roadmap to production

In dependency order. Steps 1–3 are enough to put Claude users behind the wall; 4–6 harden it.

1
Move raw data out of the repo into a governed store with column tags mirroring policy.classify().
Keep code, tests, templates and a synthetic fixture in git. This alone closes the file-system bypass for Claude Code.
2
Stand up the MCP server (remote, OAuth 2.1, per-user tokens) exposing search_targets, get_target, get_dossier, segment_stats.
Every tool result passes through guard(); get_dossier additionally checks pitch_visible(). Contract-test each tool per role.
3
Connect the IdP — SSO on the Claude workspace, groups → one role family per user, role and scope as token claims.
Register the MCP connector org-wide; users authorise with their own login.
4
Row-level ABAC — territory / deal-team predicates in the warehouse, evaluated on the caller's claims.
Wildcard scope forbidden for any role whose ceiling includes dossiers, contacts or pipeline.
5
Audit stream to WORM + SIEM, with alerts on downgrades, unmasks, exports and bypass attempts.
One stream serves SOX ITGC, GDPR Art. 30 and insider-trading surveillance.
6
SDC service for Data Science — k≥5, dominance and complementary suppression; MNPI-bearing signals excluded from the mart.
Replaces the blunt per-record refusal with governed aggregates that still answer real questions.
